# Design Proposal: SwiftKeychain 0.3.0 — a label, and one prompt for a burst of reads

**Status:** Shipped in 0.3.0, 2026-10-28 (see §18). Proposed 2026-10-28. Scope: the two items left in the 0.2.0 roadmap's "Later"; the user asked
for both as 0.3.0 on 2026-10-28.

## 1. Objective

1. An item can carry a label, so Keychain Access shows a name rather than only the service.
2. Several reads of items that ask for the person, close together, ask the person once.

## 2. Motivation

- **Label.** FleetWatch's own Keychain code labelled its items "FleetWatch sign-in" and "FleetWatch
  Reporter". Moving onto 0.1.1 dropped them, so a person looking in Keychain Access sees only the
  service name. The 0.2.0 proposal (§14) deferred this until a migration needed it; one has.
- **One prompt.** An app that signs a release reads the signing key, then a notarisation token, then
  perhaps the key again. With 0.2.0 each read shows the system prompt. Three prompts for one act teach
  the person to approve prompts without reading them, which is the habit presence exists to break.

## 3. Proposed Architecture

### 3.1 Label

`KeychainItem.label: String?`, default `nil`, the last `init` parameter so existing calls compile.

- `SystemKeychain` sends it as `kSecAttrLabel` on add and in the changes of an update, so storing
  again with a new label renames the item.
- It is **not** part of the item's identity: queries that find, update or delete an item don't carry
  it. An item stored by 0.2.0 without a label is still found by an item that has one, and a label
  change updates the item rather than adding a second.
- `nil` sends nothing: it leaves whatever label the item already has. There is no way to remove a
  label short of deleting the item; nothing has asked for one.
- `InMemoryKeychain` keeps the rule: its key is already service, account, access group and
  synchronizable, and stays so.

### 3.2 Reuse: what the Keychain offers

`SecItem.h`, on `kSecUseAuthenticationContext`: "If the specified context has been previously
authenticated, the operation will succeed without asking user for authentication", and a context not
yet authenticated is authenticated by the call, "allowing caller to eventually reuse the successfully
authenticated context in subsequent keychain operations." So one `LAContext`, passed to each read, asks
once. The context has no expiry of its own: once authenticated it stays so until `invalidate()`.
The bound has to be ours.

(`LAContext.touchIDAuthenticationAllowableReuseDuration` is something else: it lets a recent *device
unlock* by Touch ID count, and does nothing for passcodes or for later reads.)

### 3.3 Reuse: the API

An opt-in on each store, off by default:

```swift
SystemKeychain(dataProtection: true, presenceReuse: .seconds(30))
InMemoryKeychain(presence: answer, presenceReuse: .seconds(30), now: clock)
```

- **Default `nil`: each read asks**, as in 0.2.0.
- **Bounded.** The window opens when the person confirms, and lasts `presenceReuse` from then. It does
  not slide: a read inside it doesn't extend it. It is capped at
  `SystemKeychain.maximumPresenceReuse`, five minutes (the same ceiling Apple sets for reusing a Touch
  ID unlock); a longer value is clamped, and zero or less means no reuse. The property reports the
  window in force.
- **The prompt shown is the first read's.** Later reads in the window show nothing, so their prompts
  aren't seen.
- **A refusal opens nothing.** A cancelled or failed prompt, or any other error, ends the window and
  drops the context: the next read asks again. A read that finds nothing asked nothing, so it opens
  nothing either.
- **`endPresenceReuse()`** ends the window at once, for sign-out or "lock now".
- **Replaces count.** `store` over an existing presence item may ask (0.2.0); it uses the same
  context, so the two stores agree that nothing in the window asks.
- **Copies share.** `SystemKeychain` is a struct; its copies share one window. Two keychains made
  separately have their own.

### 3.4 Thread safety

`LAContext` is not `Sendable`, and Apple doesn't document it as safe to use from two threads at
once. The context lives inside an `OSAllocatedUnfairLock`, and each presence read runs its Keychain
call **while holding the lock**, building its query inside it. The context never leaves the lock.

That also serialises a concurrent burst: a second read waits for the first's prompt and then reuses
its answer, instead of showing a second prompt beside it. The cost is that presence reads through one
keychain don't overlap; they block their caller for the prompt anyway. Reads of items that don't ask
for the person never take the lock.

The lock's state must be `Sendable`, which `LAContext` isn't, so it is held in a small final class
marked `@unchecked Sendable`, justified inline: it is only touched while the lock is held.

### 3.5 Platforms

tvOS and watchOS can't ask for the person (`canAskForPerson`), and `SystemKeychain` refuses presence
items there before anything else. `presenceReuse` compiles there, reports `nil`, and does nothing.
The macOS login keychain refuses presence items too, so reuse has nothing to do there either.

### 3.6 `InMemoryKeychain`

Models the same rule so an app can test it: within the window its `presence` closure isn't called;
after it, or after a refusal or `endPresenceReuse()`, it is. It takes the time from a `now` closure
(default `ContinuousClock.now`) so a test can step past the window without sleeping. The check and
the prompt run under one lock, as in `SystemKeychain`, so a concurrent burst asks once there too.

## 4. API Surface

```swift
public struct KeychainItem {
    public var label: String?                                  // new, default nil, last in init
}

public struct SystemKeychain {
    public static let maximumPresenceReuse: Duration           // five minutes
    public let presenceReuse: Duration?                        // the window in force
    public init(dataProtection: Bool = true, presenceReuse: Duration? = nil)
    public func endPresenceReuse()
}

public final class InMemoryKeychain {
    public let presenceReuse: Duration?
    public init(presence: … = { _ in .granted }, presenceReuse: Duration? = nil,
                now: @escaping @Sendable () -> ContinuousClock.Instant = { .now })
    public func endPresenceReuse()
}
```

## 7. Source & API Compatibility

Additive. Every new parameter is defaulted and appended. `KeychainItem`'s synthesized `Hashable` now
includes the label, so two descriptions that differ only by label are unequal; the Keychain still
treats them as one item.

## 10. Test Strategy

- **Label:** the default; `addAttributes` carries `kSecAttrLabel` when set and not when `nil`; read
  queries never carry it; in both stores, an item stored with a label is found by one without, and a
  re-store with another label leaves one item; in the login keychain, the label is read back from the
  stored attributes, and a re-store renames it.
- **In-memory reuse:** off by default (two reads, two prompts); on, three reads ask once with the
  first prompt; after the window, again; a refusal opens nothing; `endPresenceReuse()`; the window
  doesn't slide; a replace inside it doesn't ask; clamping.
- **SystemKeychain:** the window's clamping and its platform answer; the shared context is handed
  out under the rules above (same object and first prompt inside the window; a new one after
  expiry, refusal, a not-found read, or `endPresenceReuse()`; a new one every time with reuse off);
  the read query carries the context it was given.
- **What can't be tested:** that the Keychain really skips the second prompt. The runner is unsigned,
  so the data-protection keychain won't store for it, and presence items exist nowhere else. The
  evidence is Apple's header (§3.2); a signed app must confirm it.

## 12. Adversarial Review

- *"A window means a malicious read inside it is silent."* Yes: that is what reuse is. Hence opt-in,
  a ceiling, no sliding, and `endPresenceReuse()`. An app that can't accept it leaves it off.
- *"The second read's prompt is lost."* By design, and documented: the person approved the first
  read's reason, so an app should use reuse only where the reads in a burst serve one act.
- *"Holding a lock across a prompt."* Only presence reads take it, and they block for the prompt
  regardless; the alternative, sharing an `LAContext` across threads unsynchronised, rests on a
  thread-safety promise Apple hasn't made.

## 13. Alternatives Considered

- **A scoped value per burst** (`keychain.withPresence(prompt:) { burst in … }`): explicit, and the
  window is the closure. But the protocol's calls would need a context parameter, or the burst would be
  a second `KeychainAccess` that every adapter (`KeychainTokenCache`, `KeychainClientStorage`) must be
  rebuilt around per burst. A setting on the store reaches the adapters unchanged.
- **`evaluatePolicy` up front**, then reads: shows a prompt even when the item turns out to be absent,
  and needs async LocalAuthentication in a synchronous API.
- **A sliding window:** a steady trickle of reads would never ask again. Rejected for that.

## 16. Open Questions

None blocking. Chosen: five-minute ceiling; window from the confirmation, not sliding; replaces
share the window.

## 18. Decided while building

- **Status:** shipped in 0.3.0 on 2026-10-28, as proposed.
- **The context is stored as `AnyObject?`, in a `HeldContext` box marked `@unchecked Sendable`** with
  an inline justification: `OSAllocatedUnfairLock`'s checked `withLock` needs `Sendable` state, and the
  alternative, `init(uncheckedState:)` with `withLockUnchecked`, hides the same claim without saying
  why. The box is only read or invalidated inside the lock.
- **One path for every call that may ask.** `SystemKeychain.authenticating(_:_:)` runs a read or a
  replace with no context (an item that doesn't ask), a fresh context (no reuse: today's behaviour,
  no lock taken), or through `PresenceSession` (reuse). The call reports `confirmed`, `notAsked` or
  `refused`; only `confirmed` with a new context opens the window.
- **`readQuery(for:)` kept, `readQuery(for:context:)` added**, so 0.2.0's query test is unchanged and
  the reuse path builds its query inside the lock.
- **Without reuse `InMemoryKeychain` doesn't take the window lock** either, so its `presence` closure
  runs as it did in 0.2.0.
- **A test was wrong first.** It used `ObjectIdentifier` inequality to show a new context, but a freed
  `LAContext` can leave its address to the next. Identity now shows only sameness; a new context shows
  itself by carrying the new read's prompt.
- **`presenceReuse` reports `nil` on tvOS and watchOS** (the session is made with no window there).
- **Verified:** `SecItem.h` (macOS 27 SDK), on `kSecUseAuthenticationContext`: a previously
  authenticated context makes the operation "succeed without asking user for authentication".
  `LAContext` has no expiry of its own, hence our bound and `invalidate()` when a window ends.
- **Not done:** a real prompt. The runner is unsigned and can't store a presence item, so nothing here
  shows the Keychain skipping the second prompt. Recorded in the master plan for the first signed app
  that uses `presenceReuse`.
